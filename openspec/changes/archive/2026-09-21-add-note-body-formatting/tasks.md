## 7. Bug fixes from real user testing

Automated/synthetic typing in this session never triggers real IME composition events (verified directly: it inserts whole strings via a single `input` event with `isComposing: false`), so neither of these was caught by the verification in section 6. Both were reported by the user testing with a real Korean IME.

- [x] 7.1 Fix: a line ending in a Korean syllable had its last character duplicated onto the next line when splitting via Enter. Root cause: `splitLine()` read `textContent` synchronously in the `keydown` handler with no guard for composition state, racing the IME's commit of the composed character. Fixed by checking `event.isComposing` at the top of `handleKeydown` and returning immediately (skipping Tab/Enter/Backspace handling entirely) while a composition is in progress. Verified two ways: (1) directly dispatching a synthetic `keydown` with `isComposing: true` and confirming the handler neither calls `preventDefault()` nor mutates any line; (2) confirming a normal (non-composing) Enter immediately after still splits correctly with the full text intact. Also updated `specs/note-taking/spec.md`'s two "Typing the marker alone" scenarios and design.md were already accurate for this; no spec change was needed for this particular bug since it was a pure implementation defect, not a described-then-violated behavior.
- [x] 7.2 Fix: pressing Backspace at the start of an empty confirmed heading or list item (e.g. a trailing empty list item created by pressing Enter once too many) reverted it to a marker-only plain-text line instead of removing it, leaving a stray `- ` or `## ` floating in the body. Fixed: Backspace at position 0 of an empty confirmed line with a preceding sibling now removes the line entirely and places the caret at the end of the preceding line, instead of reverting to plain text. Non-empty confirmed lines, and empty confirmed lines with no preceding sibling, still revert to plain text as before (verified both as regression checks). Updated `specs/note-taking/spec.md` to document this as the specified behavior (new scenarios: "Backspace on an empty subheading/list item deletes the line instead"), since this changes what the existing "Backspace reverts ... to plain text" scenarios describe for the empty case specifically.
- [x] 7.3 Fix: selecting a range of text starting at the very beginning of a confirmed heading/list-item line and pressing Backspace reverted the line to plain text instead of deleting the selected text — the Backspace handler only checked caret offset 0, not whether the selection was collapsed. Confirmed this did not conflict with the existing spec (every "Backspace reverts..." scenario already specifies "the caret," implying a collapsed caret, not an active selection) before fixing, per the user's explicit instruction to report rather than fix if it did conflict. Fixed by adding a `selection.isCollapsed` check to the revert/delete-line condition, so a non-collapsed selection at offset 0 now falls through to normal `contenteditable` selection-deletion instead. Verified the type-preservation half directly (selecting "abc" of a confirmed heading "abcdef" and pressing Backspace leaves it a heading, not a plain paragraph); verified the deletion half via `document.execCommand('delete')` after re-establishing the same selection, since this automation environment's synthetic Backspace keydown does not trigger the browser's native contenteditable deletion when correctly left un-prevented (analogous to the earlier IME-composition automation limitation) — end state confirmed as `{lineType: "heading", text: "def"}`. Added two new spec scenarios ("A text selection starting at line start deletes the selection instead of reverting") for both subheading and list-item requirements.
- [x] 7.4 Fix: pressing Up/Down arrow keys (or any caret movement) after reverting a heading/list-item to plain text via Backspace would silently re-confirm it back into styled form. Root cause: `revertLine()` restores marker-prefixed text (e.g. `## my heading`) indistinguishable from a freshly-typed unconfirmed line, so the `selectionchange`-based passive-confirmation trigger (used to detect focus moving between lines, including via arrow keys) re-triggered `confirmLine()` on it. Fixed with a `data-reverted` flag set in `revertLine()`, checked by a new `confirmOnLeave()` wrapper used only at the two passive trigger sites (`handleFocusOut`, `handleSelectionChange`) — not at the Tab handler, so an explicit Tab press can still deliberately re-confirm a reverted line. The flag clears on the next `input` event on that line (further typing is explicit re-engagement). Verified in the running app via DOM/Selection inspection: confirmed a heading, reverted it via Backspace, pressed Up then Down twice across it, and confirmed it remained `{lineType: "paragraph", text: "## my heading"}` throughout rather than snapping back to a heading. Added two new spec scenarios ("Navigating away from a reverted line does not re-confirm it") for both subheading and list-item requirements.
- [x] 7.5 Fix: typing `## heading`/`- item` and pressing Enter (without ever pressing Tab) split the line but left it as literal plain text instead of confirming it, contradicting the existing spec text (both "Losing focus also confirms..." scenarios already list "pressing Enter to start a new line" as an example of the focus-loss trigger, and design.md's trigger-point list does the same) — no spec change needed, this was a pure implementation gap. Root cause: the `Enter` branch of `handleKeydown` called `splitLine()` directly without ever confirming the original line first, and `splitLine()` pre-updates `activeLineEl` to the new line before the `selectionchange` event fires, so the passive `handleSelectionChange` trigger saw no line change to react to and never confirmed the original line either. Fixed by calling `confirmOnLeave(lineEl)` before `splitLine(lineEl)` in the Enter branch (using `confirmOnLeave`, not `confirmLine` directly, so a `data-reverted` line from 7.4 still correctly does not re-confirm on Enter — consistent with Enter being categorized as a focus-loss trigger, the same bucket as arrow keys). Since `confirmLine` strips the marker text via `setLineContent`, which invalidates any Range into the old text node, added a `placeCaretAtOffset()` helper and used it to re-place the caret at the equivalent post-strip offset (`preOffset - markerLength`) so `splitLine`'s subsequent `caretOffsetInLine()` read still splits at the intended point. Verified in the running app: (1) `## heading` + Enter now immediately renders as a heading with a new empty paragraph below and caret at its start; (2) placing the caret mid-text (`## abc|def`) and pressing Enter correctly produces a confirmed heading "abc" and a plain paragraph "def" (heading doesn't continue); (3) same mid-text split on a `- abc|def` list item correctly continues both halves as depth-0 list items; (4) a Backspace-reverted heading (`data-reverted: true`) pressed with Enter does not re-confirm, splitting as plain text as expected.
- [x] 7.6 Fix (two related reports, same `splitLine()` root cause): (a) there was no way to stop a list and go back to plain paragraphs — pressing Enter on an already-empty confirmed list item just created yet another empty list item below it, forever; only Backspace (which deletes the line) existed as an out, which isn't the same as "keep typing as plain text here." (b) pressing Enter at the very start of a non-empty confirmed heading moved the heading's own text down into a new plain-paragraph line, while the original (now-empty) line kept its heading styling — visually indistinguishable from "the heading turned into a paragraph," when the actual desired behavior is the heading itself (unchanged, full text) moving down with a new blank paragraph inserted above it. Fixed both in `splitLine()` with two early-exit special cases before the general split logic: (a) if the current line is a list item with no text content, convert it in place to a plain paragraph (clearing its depth) and do not create any new line; (b) if the caret is at offset 0 of a non-empty line, insert a new empty plain paragraph *before* the current line via `lineEl.before(...)` and leave the current line completely untouched, placing the caret back at its start. Verified in the running app: confirmed heading with full text, caret at position 0, Enter → empty paragraph appears above, heading (unchanged, full text) is now the second line; empty confirmed list item at depth 1, Enter → converts in place to an empty plain paragraph with no depth, no new line added; regression-checked that a non-empty list item split at a non-zero offset still continues both halves as list items at the same depth (unchanged), and that Enter on an already-empty heading still creates a new blank paragraph below rather than triggering either special case (unchanged, since neither condition — "list-item and empty" nor "offset 0 and non-empty" — matches an empty heading).
- [x] 7.7 Correction to 7.6(b): after seeing it in the app, the user pointed out that pushing a non-empty *list item* down the same way as a heading looks wrong — it inserts an unrelated plain paragraph into the middle of what should read as one continuous list, breaking the list's visual continuity. Narrowed the condition to `offset === 0 && text.length > 0 && currentType !== 'list-item'`, so list items now fall through to the general split path instead, which already produces the desired result for them: two list items at the same depth (an empty one where the caret was, followed by one holding the original text) — no foreign paragraph type inserted. Headings are unaffected by this narrowing. Verified in the running app: a confirmed list item with content, caret at position 0, Enter → splits into two consecutive list items at the same depth (no plain paragraph in between); re-verified the heading case is unchanged (empty paragraph inserted above, heading moves down intact). Updated the corresponding list-item spec scenario to describe the two-list-items outcome instead of the push-down-with-a-blank-paragraph-above outcome.
- [x] 7.8 Redesign of Backspace-at-line-start for non-empty confirmed lines, replacing the original "always revert to plain text with the marker restored" rule (which is what the still-unstarted "only apply when empty" ask from earlier resolved into once the user specified concrete replacement behavior per type):
  - **Subheading with content:** if the immediately preceding line is an empty plain-text line, Backspace removes only that line and leaves the subheading completely untouched (its text, type, and style all unaffected) — this specifically targets the empty spacer line that 7.6(b)'s "push heading down" Enter fix routinely creates just above a heading. Otherwise, Backspace merges the subheading's text onto the end of whatever line precedes it (plain text, a list item, or another subheading), drops the subheading's own styling, and removes the subheading's line — ordinary "Backspace joins with the previous line" behavior. If there is no preceding line at all, Backspace does nothing (`event.preventDefault()` still applies, so nothing falls through to native deletion either).
  - **List item with content:** unchanged mechanism (reverts in place to plain text, no merge into the previous line), but `revertLine()`'s list-item branch no longer restores the `  - ` marker/indentation as literal text — it now leaves only the bare `text`. This also improves the still-existing "empty list item, no preceding line" revert path, which previously left a floating `- ` and now leaves genuinely empty text.
  - Implemented as new branches in the `Backspace` handler in `handleKeydown` (heading: check `prevEl`'s type/emptiness, then either `prevEl.remove()` or merge via `setLineContent(prevEl, prevEl.textContent + lineEl.textContent)` + `lineEl.remove()` + `placeCaretAtOffset(prevEl, mergeOffset)`; list-item: unchanged call to `revertLine()`) plus the one-line `revertLine()` change dropping list-item marker restoration. The empty-line branch (delete-if-preceding-exists, else revert-with-marker) is completely unchanged.
  - Verified in the running app: (1) heading with content, empty paragraph immediately above, Backspace → the empty paragraph is removed, heading unchanged; (2) heading with content, a list item above with its own content, Backspace → list item's text becomes `"<original><heading text>"`, still a list item at its original depth, heading line gone, caret at the join point; (3) list item with content at depth 2, Backspace → reverts in place to a plain paragraph containing only the bare text, no marker/indentation; (4) heading with content and no preceding line at all, Backspace → no change; (5) regression: empty heading with a preceding line still just deletes the line as before; (6) regression: a non-collapsed text selection starting at offset 0 still deletes the selection rather than triggering any of the above (the `selection.isCollapsed` guard from 7.3 short-circuits before any of this runs). Updated `specs/note-taking/spec.md`: rewrote the subheading requirement's Backspace rule and replaced its single "reverts to plain text" scenario with three scenarios (empty-line-above removed unchanged, merge-into-preceding-line, no-preceding-line no-op); updated the list-item requirement's Backspace rule and its scenario to describe marker-free reversion.

## Context

The note body is currently a plain `<textarea>` in [NoteEditPanel.svelte](../../../src/lib/components/NoteEditPanel.svelte), two-way bound to `draft.body`, with autosave triggered on `oninput`. `Note.body` is a plain `string` all the way down: `LocalStorageNoteStore` serializes it as-is, the search feature (`add-note-search`) matches raw substrings against it, and `NoteCard`'s preview takes the first 80 characters of it verbatim. `DESIGN.md`'s layout rules explicitly commit to mobile-first design ("모바일 웹을 기준으로 우선 설계"). See proposal.md for why this change is happening and what was explicitly dropped (date blocks, multiple heading levels, rich text) during exploration.

## Goals / Non-Goals

**Goals:**
- Add one subheading level and 4-level nested lists, authored via an explicit Tab-confirm gesture that is safe for CJK IME composition.
- Keep `Note.body` a plain string — no data migration, no changes to `NoteStore`, search, or autosave wiring.
- Keep the feature actually usable on mobile, where on-screen keyboards have no Tab key.

**Non-Goals:**
- Date blocks, multiple heading levels, bold/italic/links/tables — explicitly out of scope per the proposal.
- Pixel-perfect multi-block copy/paste or a custom undo/redo stack — this relies on the browser's native `contenteditable` undo/redo and accepts its rough edges.
- Depth changes (Tab/Shift+Tab on an existing list item) on touch-only devices — this is a known, accepted gap; see Risks.

## Decisions

### `Note.body` stays a plain string; only the editing surface changes
The editor works entirely by parsing `body` into lines and re-serializing lines back into `body` on every change. A confirmed heading line serializes as `## <text>`; a confirmed list item at depth *d* serializes as `<d*2 spaces>- <text>`; anything else serializes as its literal text. This is why nothing downstream (storage, search, autosave, the two-panel layout) needs to change — `body` after this change is still exactly the kind of string those things already handle, just one that may contain `## `/`- `-prefixed lines.

### Why plain `<textarea>` can't do this, and why `contenteditable` is used instead
A `<textarea>` cannot style part of its content differently from the rest (no bigger font for one line, no indentation for another) — that requires real DOM elements per line, which means `contenteditable`. The new `NoteBodyEditor.svelte` component owns a single `contenteditable` container; each line of `body` is one child element (a `<div>` or `<p>`/`<li>` depending on its confirmed type) so styling can be applied per line without touching sibling lines.

### The "never rewrite the line under active composition" rule
`contenteditable` DOM rewrites *while* a CJK IME composition is in progress are the classic cause of corrupted/duplicated characters and cursor jumps — this is why Notion/Obsidian-style live-as-you-type rendering was rejected during exploration. The rule this design commits to: **the line that currently has the caret is never restyled while the user keeps typing into it.** It is re-evaluated (checked against the `## `/`- ` patterns, and possibly restyled) only at specific, discrete trigger points — never on every keystroke or on every `input` event on that line.

This rule alone wasn't sufficient in practice: the first implementation still read/rewrote a line's `textContent` synchronously inside the `keydown` handler for Enter (to split the line), with no guard for composition state. For a line ending in a Korean syllable, pressing Enter to commit the composition and pressing Enter to create a new line look identical at the `keydown` level, and the composed character isn't necessarily committed into the DOM yet when that `keydown` fires — reading `textContent` at that exact moment could read stale content, and the delayed IME commit landing after our own split then duplicated the last character onto the new line. This was found via real user testing (this behavior doesn't reproduce through synthetic/automated typing, which doesn't go through real composition events at all) and fixed by checking `event.isComposing` at the very top of the keydown handler and returning immediately if true — Tab, Enter, and Backspace all skip their custom handling entirely while a composition is in progress, leaving the browser's native composition-commit behavior alone.

### Trigger points for confirmation
1. **Tab**, pressed while the caret is on a line matching `## ` or `- ` (not yet confirmed) → confirms that line's block type.
2. **Tab**, pressed while the caret is on an already-confirmed list item → increases its depth (capped at 3). **Shift+Tab** decreases it (floored at 0).
3. **The line losing focus** — caret moves to a different line by any means (click/tap elsewhere, arrow keys, pressing Enter to start a new line) — confirms an unconfirmed `## `/`- ` line the same way Tab would, but does **not** perform a depth change (there's no "how many levels" signal in a plain focus change). This trigger is what keeps the feature usable on mobile, where there is no Tab key at all on the standard on-screen keyboard; see Risks for what remains desktop-only.
4. **Opening or switching to a note** — the entire `body` is parsed fresh and every matching line renders in its confirmed style immediately. Nothing is "unconfirmed" on load; the raw/unconfirmed state only exists transiently, for the one line currently being typed into.
5. **Backspace at the start of a confirmed line.** This trigger only fires for a **collapsed caret** at offset 0 — an active text selection that happens to start at offset 0 is a content edit (delete the selection), not a request to revert the line; see the "selection-aware Backspace" bug fix below. What Backspace actually does then diverges by content and by line type — see "Backspace at line-start diverges by type and content" below for the current behavior and how it got there.

Any other key on any other line is untouched — normal `contenteditable` text editing.

### Enter must confirm the line it splits, same as any other focus-loss trigger
Trigger point 3 above already names "pressing Enter to start a new line" as one way the caret can leave a line, and the spec text this design.md exists to describe has always required it to confirm the line just like any other focus-loss case. The first implementation's `Enter` handler called `splitLine()` directly and never routed through the confirmation check at all — and because `splitLine()` proactively updates the tracked "current line" to the newly-created line before the browser's `selectionchange` event fires, the passive `selectionchange`-based trigger (the one arrow keys and clicks rely on) also saw no line change to react to. Net effect: typing `## heading` and pressing Enter left the original line as literal plain text indefinitely, only fixable by then leaving it via some other means (arrow key, click, blur). Fixed by explicitly confirming the line (respecting the `data-reverted` guard below, since Enter belongs to the same focus-loss trigger bucket as arrow keys) immediately before splitting it, with the caret re-placed at the equivalent post-confirm offset so the split point doesn't shift.

### Splitting a line must never make its own type ambiguous
Two related user reports both traced back to the same generic slice-and-create logic in `splitLine()`, which always treated the caret position as "content before stays here, content after moves into a new line" without special-casing the edges. Two edge cases needed their own explicit handling instead:
- **Enter at the very start of a non-empty confirmed heading.** Splitting generically here produces `before = ''`, `after = <the whole original text>` — the original element keeps its type/styling but goes empty, and a *new* element carries the real text (as a plain paragraph, since new lines are never automatically the same type as what they split from). The user sees this as "the heading turned into a paragraph," which is the opposite of what actually happened structurally, and not what anyone wants: they want the heading itself, unchanged, to just move down a line. Fixed by special-casing `offset === 0 && text.length > 0 && currentType !== 'list-item'`: insert a new empty plain paragraph *before* the line instead of splitting it at all, and leave the original element (and its content and type) completely untouched. List items are deliberately excluded from this case: applying the same fix there would insert an unrelated plain paragraph in the middle of a visually continuous list, which reads as broken list continuity rather than "the item moved down." For a list item, the generic split path already does the right thing — it produces two list items at the same depth (an empty one, then one with the original text) — so list items at offset 0 fall through unchanged.
- **Enter on an already-empty confirmed list item.** The generic path treats this exactly like continuing the list — it creates yet another empty list item below and leaves the original (also still empty) one behind, so a user who wants to stop making list items after the last one has no way to do it without deleting content (Backspace on an empty item deletes the line per §7.2, which isn't "keep typing here as plain text"). Fixed by special-casing `currentType === 'list-item' && text.length === 0`: convert the current (empty) line in place to a plain paragraph and create no new line at all — the same gesture that would otherwise create a redundant empty list item instead ends list formatting.

Both fixes are pure implementation corrections to `splitLine()`'s edge-case handling; neither changes any already-specified scenario in `spec.md`, since no existing scenario described what Enter should do at offset 0 or on an empty list item.

### Backspace at line-start diverges by type and content
The original version of this trigger applied one rule uniformly to every confirmed line with content: revert it to plain text in place, restoring its literal marker. Two problems surfaced with real use: the "push heading down" Enter fix above routinely leaves an empty plain-paragraph spacer line directly above a heading, and reverting the heading when Backspacing into that spacer felt wrong — the heading isn't the thing the user is trying to undo, the spacer is. Separately, restoring a list item's `  - ` marker as literal text (spaces and all) was never actually useful — nobody backspaces into a list item wanting to see the raw marker again, they want it to just become normal text. This led to splitting Backspace-at-start's non-empty-line behavior by type instead of one shared rule:

- **Subheading, content present.** The line above matters: if it's an empty plain-text line, that line is almost certainly leftover scaffolding (e.g. from the push-down Enter fix) — Backspace removes only that spacer and leaves the subheading completely untouched, still styled, still in place. Otherwise (the line above has content, is itself a list item or subheading, or doesn't exist), Backspace merges the subheading's text onto the end of whatever's above and removes the subheading line, dropping its subheading styling in the process — ordinary "Backspace joins this line with the previous one" behavior, with the wrinkle that a subheading isn't allowed to survive a merge into another line's content. If there's no line above at all, there's nothing to merge into and nothing to delete, so Backspace does nothing.
- **List item, content present.** No merge, no special-casing based on what's above — it still reverts in place to plain text the same way it always did, just without restoring the `- `/indentation marker text (see `revertLine()`, whose list-item branch now returns the bare text unchanged instead of `` `${'  '.repeat(depth)}- ${text}` ``). This one `revertLine()` change also incidentally cleans up the still-existing empty-list-item-with-no-preceding-line revert path (trigger 5's "no preceding line" fallback), which now leaves genuinely empty plain text instead of a floating `- `.

Empty confirmed lines (of either type) are unaffected by any of this — the existing empty-line rules (delete if a preceding line exists, otherwise revert-with-marker) stand exactly as before section §7.2 left them.

### Reverting a line must stick until the user explicitly re-confirms it
`revertLine()` restores the literal marker text (e.g. `## my heading` for a reverted heading), which is indistinguishable from a line the user just freshly typed. Without extra state, this created a bug: any passive confirmation trigger (losing focus, or the `selectionchange`-based line-tracking used to detect focus changes between lines) that later passes over that same line — for instance, arrow-keying past it — would silently re-confirm it, undoing the user's explicit Backspace-revert with no further action on their part. Fixed with a `data-reverted` flag set by `revertLine()` and checked by a `confirmOnLeave()` wrapper used only at the two *passive* trigger sites (focus-loss, `selectionchange`-based line-change detection) — **not** at the Tab handler, since an explicit Tab press should still be able to deliberately re-confirm a reverted line. The flag is cleared as soon as the user types into that line again (in the `input` handler), since further edits are explicit re-engagement with the line and it should become eligible for confirmation again like any other line.

### List depth representation
Depth is stored as leading spaces before `- ` in the serialized string — 2 spaces per level (`- ` at depth 0, `  - ` at depth 1, `    - ` at depth 2, `      - ` at depth 3), a conventional, human-readable nested-markdown-list convention. This is also what makes "on reopen" parsing trivial: depth is `floor(leadingSpaces / 2)`, clamped to the 0–3 range.

### `DESIGN.md`: no new component, extend `typography-assets` and add one token
A subheading and a list-item are not new interactive components with their own states — they're a typographic/spacing treatment applied inside the existing body-editing surface. This adds:
- A new type role, `body-heading`, to `typography-assets.roles` (distinct from `h3`, which is documented as the note-card title, not an in-body heading) — proposed as 20px/600/30px line-height, one step below `h3` (24px/600/36px) and clearly larger than `body` (16px/400/24px).
- A new spacing token is **not** needed — nested-list indentation reuses the existing `spacing-lg` (16px) per depth level, applied as `margin-left: calc(var(--spacing-lg) * depth)`.

Both go through the standard graph → review → compile → adopt pipeline, not a hand edit.

## Risks / Trade-offs

- **[Risk] List depth changes (Tab/Shift+Tab on an existing item) have no touch equivalent in this version.** A touch-only user can create list items (via the focus-loss trigger) but cannot nest them deeper than depth 0 without an external keyboard. → Accepted as a known gap for this first version; a future change could add on-screen indent/outdent controls (e.g., buttons that appear near a focused list item) without changing the underlying data model.
- **[Risk] Hand-rolled `contenteditable` editors are notoriously fragile for things this design explicitly doesn't try to solve** — multi-line selection + delete/paste, browser-specific undo/redo quirks, and cross-browser caret-position restoration after a line re-renders. → Accepted per the proposal's explicit non-goals; if these prove too rough in practice, a future change could reconsider a small editor library rather than continuing to hand-roll fixes. Four instances of exactly this fragility were found via real user testing (not caught by automated testing, which can't simulate real IME composition) and fixed: the Enter/IME race described above; Backspace-at-start not restoring caret position at all (defaulted to position 0 regardless of `atStart`/`atEnd` intent); Backspace with an active (non-collapsed) selection starting at offset 0 incorrectly reverting the line instead of deleting the selected text; and a reverted line getting silently re-confirmed by a later passive trigger (e.g. arrow-key navigation). All four fixed without any change to the spec's described behavior for the collapsed-caret case — the selection case was previously unspecified, not contradicted, since every existing Backspace scenario already describes "the caret," implying collapsed.
- **[Trade-off] The focus-loss trigger means a line can "surprise-confirm"** if the user taps away mid-thought, planning to come back and keep editing the marker line as plain text. → Accepted: Backspace-to-revert (already in scope) is the recovery path, and this trade-off is what makes the feature workable on mobile at all.

### Considered and declined: splitting `NoteBodyEditor.svelte` by line type
After all the fixes above accumulated, the file was reviewed for whether `heading`/`list-item`/`paragraph` handling should be split into separate modules (e.g. one handler per type). Declined for now: the complexity here isn't a file-organization problem, it's that the actual behavior is inherently cross-type — a heading's Backspace-at-start outcome depends on the *previous* line's type (merge into it, or delete it if it's an empty paragraph), and `revertLine`/`splitLine` already have to reason about more than one type per call to produce a consistent result. Splitting by type would move that same cross-type knowledge into shared state passed between modules (`activeLineEl`, `placeCaret`, `setLineContent`, etc.) without removing it, trading a few large functions for more, smaller ones stitched together with more indirection. At the current scope (two confirmable types, ~300 lines) the split isn't worth it; it would be worth revisiting if more line types are added later (e.g. quote blocks, code blocks) and their behaviors turn out to be genuinely independent of each other, which would let a type-strategy-object pattern pay for itself.

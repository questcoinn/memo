## Context

`NoteBodyEditor.svelte` (see `add-note-body-formatting`) renders each line of `body` as one block-level `<div data-line-type="...">` with a single text node as its content (`setLineContent()` does `el.textContent = text`). Every helper — `caretOffsetInLine`, `placeCaret`, `placeCaretAtOffset`, `serializeDom`, `revertLine`, the Backspace merge logic — reads or writes that text via `.textContent`, and `confirmLine`/`parseLineForConfirm` only recognize a marker (`## `, `- `) at the very start of a line, confirmed on Tab, the line losing focus, or Enter (`confirmOnLeave`). `BodyLine` (`body-format.ts`) is `{ type, text, depth? }` — one type and one text string per line, nothing finer-grained. See proposal.md - Why for why links were previously out of scope and why they're back in scope now.

## Goals / Non-Goals

**Goals:**
- Detect URL-shaped text (starting `http://`, `https://`, or `www.`) anywhere within a line's text and render it as a clickable link, using the exact same confirm triggers already wired up for headings/lists.
- Keep `Note.body` a plain string with no new stored shape — a link's visible text and its target are the same substring, so nothing new needs to survive serialization.
- Keep the confirmed link atomic (not editable in place), leaning on native browser caret/delete handling for it rather than hand-rolling more caret math than necessary.

**Non-Goals:**
- Editing a confirmed link's text/target in place — deleting and retyping is the only path in this version (explicitly deferred, revisit if it proves annoying in practice).
- Bare-domain detection (`example.com` with no scheme/`www.`) — too prone to false positives (version strings, abbreviations, decimal numbers) in ordinary sentences.
- Linking text in the note title — the title is a plain `<input>`, not `contenteditable`; out of scope by construction.
- Markdown-style `[label](url)` syntax — deliberately not used; see Decisions.

## Decisions

### Detection is a rendering/serialization-time transform, not new stored data
Because a link's visible text and its `href` are the same string, `BodyLine.text` doesn't need a new shape and `body-format.ts`'s line-level `parseLine`/`serializeLine` don't need to change at all. A new small, DOM-free module (e.g. `link-format.ts`, alongside `body-format.ts`) exports something like `splitIntoRuns(text: string): Run[]` (`Run = { type: 'text'; value: string } | { type: 'link'; url: string }`), used only inside `NoteBodyEditor.svelte` at the points that already write a line's content. This is also why `serializeDom()` needs **no change at all**: `Element.textContent` already concatenates the text of all descendant text nodes regardless of element wrappers in between, so a line containing `<a>https://example.com</a>` mid-text still reports its full original string through `.textContent` — the same property `caretOffsetInLine`, `revertLine`, and the Backspace heading-merge logic already rely on, so none of them need to change either. The only genuinely new code is on the *write* side (below).

### Link confirmation is a second, independent pass alongside marker confirmation
`confirmLine()` only fires when the line is currently a plain, unconfirmed paragraph (`currentType === 'paragraph'`) and the text matches a marker prefix — by design, it can't also be responsible for links, since link text can appear inside an already-confirmed heading or list item, or inside a paragraph that never matches a `## `/`- ` marker at all. So at each of the three existing trigger sites — the `Tab` branch in `handleKeydown`, `confirmOnLeave()` (used by `handleFocusOut`/`handleSelectionChange`), and the `Enter` branch's pre-split confirm step — a new, independent `confirmLinks(lineEl)` call runs *in addition to* `confirmLine()`/`confirmOnLeave()`, regardless of whether those returned true or false. `confirmLinks()` walks `lineEl.childNodes`, leaves existing `<a>` children untouched (already confirmed, don't re-scan their text), and for every plain Text child runs `splitIntoRuns()` and replaces it with the resulting Text/`<a>` sequence. Because this only ever runs from those three trigger call sites — never from `handleInput` — "typing the marker alone doesn't confirm it" holds for links the same way it already does for headings/lists, with no extra guard needed.

### The confirmed link is a real, atomic `<a href>`
`contenteditable="false"` on the anchor makes it a single unit for the browser's own caret navigation and deletion — arrow keys skip over it, and Backspace/Delete adjacent to it removes the whole element without us hand-rolling that specific caret math. It's a real `<a href="...">` (not a styled `<span>`) so the browser's native right-click "copy link address" / "open in new tab" context menu works for free. `contentEditable="false"` does **not**, however, suppress the anchor's native click-to-navigate action — that fires regardless, so a plain click was found (via real user testing, not caught by this project's automated click testing — see Risks) to navigate away instead of just placing the caret. Click handling always calls `preventDefault()` once the click target resolves to `.inline-link`, and only additionally opens the link in a new tab when a Cmd/Ctrl modifier is held.

### `placeCaretAtOffset` needs to walk multiple children, not just the first
It currently assumes `lineEl.firstChild` is the line's one and only text node. Once a line can contain `Text, <a>, Text, ...` sequences, it needs a small tree-walk: accumulate each child's text length until the target offset falls within a Text child (place there) or exactly at a boundary next to an `<a>` (place immediately before/after it, never inside). `caretOffsetInLine` does **not** need the equivalent change — it derives an offset from an existing, browser-placed Range via `Range.toString().length`, which already accounts for atomic children correctly since the browser itself only ever places the Range's boundary before or after an atomic node, never inside it.

### Backspace-at-offset-0 for a plain paragraph is handled explicitly, never left to native merge
Before this feature, an offset-0 Backspace was only ever intercepted for a *non*-paragraph line (heading/list-item) — a plain paragraph fell through to the browser's own native `contenteditable` div-merge behavior, untouched by this project's code at any point since headings/lists were introduced. That was never actually verified to produce consistent, correct DOM structure; it happened not to matter as long as merged content was always plain text either side. Once a line can contain an atomic `<a>`, real user testing found the native merge corrupts structure in a way that only surfaces on a *later* interaction (a subsequent Enter split lands at an unrelated point) — see tasks.md §9.5's exact 5-step repro. Fixed by adding an explicit `paragraph` branch alongside the existing heading/list-item ones, backed by a new shared `mergeLineIntoPrevious(lineEl, prevEl)` that moves lineEl's actual child nodes onto the end of prevEl — preserving any link on either side, the same "move real nodes, don't flatten through `.textContent`" reasoning `splitLineNodes` already uses for Enter. The existing heading-into-previous-line merge (previously inline, flatten-based via `setLineContent`) now reuses this same helper — fixing a latent version of the identical link-destroying bug there too, never reported because it hadn't been exercised with a link present yet.

### Splitting a line preserves links before the split point, resets them after
The original version of this decision reset *both* halves of a split line to plain text, reading only the flattened `textContent` and rebuilding everything from scratch via `setLineContent`. Real use surfaced this as more disruptive than intended — losing a link you'd just confirmed, immediately, by pressing Enter right after it, read as a bug rather than an accepted rough edge. Revised to split at the DOM level instead of the flattened-string level: `splitLineNodes()` walks the line's actual child nodes (a mix of Text and atomic `<a>` elements), keeping every node entirely before the split point as-is — including any confirmed link — and moving everything from the split point onward to the new line. Only the *new* line is flattened to plain text (via `.textContent` on the moved nodes) and rebuilt as an ordinary unconfirmed line, same as any other freshly created line. A text node straddling the split point is itself split into two; an atomic link is never split mid-span, since the caret can never actually be positioned inside one — the split point can only ever fall at its boundary (see `placeCaretAtOffset`), so the moved-vs-kept decision for a link is always clean. This keeps `splitLineNodes()` a small, self-contained addition rather than a rewrite of `splitLine()`'s overall shape.

### `DESIGN.md`: one new component, no new token
Adds a `link` component (anatomy: label; states: default, hover, focus-visible; disabled/loading/error not applicable, matching how `note-card` already documents inapplicable states) styled with the existing `color-primary` token (already restricted by foundation rule to "elements with a real action," which a hyperlink is) and `color-primary-hover` on hover, the same pair `button-primary` already uses. No new token needed. Goes through the standard graph → review → compile → adopt pipeline.

### Paste is forced through the same plain-text path as typing
The browser's default `contenteditable` paste handling doesn't insert clipboard text the way typing inserts characters — confirmed by real user testing to sometimes wrap plain-text clipboard content in a `<span>` in this browser engine. Every line-walking function in this feature (`confirmLinks`, `splitLineNodes`) only ever inspects direct children by type — a `TEXT_NODE` is scanned for URLs or split at a character offset, any other element is treated as one atomic, unsplittable, un-scannable unit (the same treatment a real confirmed link gets). A pasted wrapper element is therefore invisible to link detection and gets treated as atomic by splitting, even though it's just plain text that happens to be wrapped. Rather than teaching each of those functions to recurse into and defensively handle arbitrary pasted HTML (unbounded in principle — paste can carry far more than a stray `<span>`), a `paste` event handler on the editor always calls `preventDefault()`, reads only the `text/plain` clipboard entry, and inserts it via `document.execCommand('insertText', false, text)` — the same primitive effect as a keystroke. This means paste can never produce DOM structure that typing couldn't already produce, so nothing downstream needs paste-specific handling.

## Risks / Trade-offs

- **[Risk] Click-to-open behavior inside `contenteditable` is not fully standardized across browsers.** → Confirmed via real user testing (not caught by this project's own automated click testing, whose coordinate-based clicks mis-targeted the container div instead of the exact `<a>` pixel — a similar automation-tooling gap to the IME/native-Backspace ones already documented for this feature): a plain click's native navigation was *not* suppressed by `contentEditable="false"` as initially assumed, and fired regardless. Fixed by always calling `preventDefault()` on a click resolving to `.inline-link`, opening only on Cmd/Ctrl. See tasks.md §9.1.
- **[Trade-off] A confirmed link can't be edited in place — only deleted and retyped.** → Accepted per Non-Goals; revisit if this proves annoying in practice, per the earlier exploration decision.
- **[Trade-off] Splitting a line via Enter still resets any link in the new (*after*) line to plain text**, requiring reconfirmation there. → Accepted: real user testing confirmed the original symmetric version (resetting *both* halves) was more disruptive than intended, since it destroyed a link immediately after confirming it if Enter was pressed right after — revised so only the new line resets, per the updated Decision above. Resetting the new line specifically is still accepted, since a freshly created line is unconfirmed by construction the same way any other new line is.
- **[Risk] `confirmLinks()`'s DOM rewrite can silently reset the caret to the start of the editor** if the caret's Range pointed into the text node being replaced — the same class of bug already fixed once for `confirmLine`/`revertLine`, missed here on first implementation. Fixed by capturing the caret's line-relative offset before mutating and restoring it via `placeCaretAtOffset()` afterward. See tasks.md §9.2.
- **[Risk] The `http://`/`https://`/`www.` prefix requirement will miss some real URLs** (bare domains, `mailto:`, etc.) in exchange for far fewer false positives on ordinary sentences containing dots and abbreviations. → Accepted per Non-Goals; can be widened later if it proves too narrow in practice.
- **[Risk] Pasted text can carry browser-inserted DOM structure (e.g. a wrapping `<span>`) that the line-walking functions can't see into**, silently breaking link detection and producing split points that don't match where the user actually clicked. → Confirmed via real user testing (typing worked, pasting didn't — the report that pinned this down); not caught by this project's own automated testing since simulating a real OS-level clipboard paste isn't available in that environment, another instance of the same class of gap already documented for IME composition and native Backspace. Fixed by forcing all paste through the same plain-text insertion path as typing; see the Decision above and tasks.md §9.4.
- **[Risk] Relying on the browser's native `contenteditable` merge behavior for any case this feature doesn't explicitly own is not actually safe once atomic links exist**, even for a case (plain-paragraph Backspace-merge) that predates this feature and was never itself reported broken. → Confirmed via the user's exact 5-step repro in tasks.md §9.5 — the corruption only became externally visible on a *later*, unrelated split, not at the moment of the native merge itself, which made it hard to trace back. Fixed by handling this case explicitly instead of trusting native behavior; see the Decision above. Worth treating as a general caution: any remaining path where a line's structure changes without going through this feature's own explicit node-moving functions is a similar latent risk.

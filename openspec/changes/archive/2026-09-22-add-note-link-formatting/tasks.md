## 9. Bug fixes from real user testing

- [x] 9.1 Fix: a plain click (no modifier) on a confirmed link navigated instead of just placing the caret. Root cause: `handleClick` only checked for Cmd/Ctrl and returned early otherwise, never calling `preventDefault()` — a real `<a href target="_blank">`'s native click-to-navigate behavior fires regardless of `contentEditable="false"` on itself (that attribute only blocks editing, not the link's default action). Not caught during initial verification because this automation environment's coordinate-based clicks mis-targeted the container div instead of the `<a>` at that pixel (confirmed via `elementFromPoint`), so the untested code path never actually got exercised by a click that hit the anchor. Fixed by always calling `preventDefault()` once a click target resolves to `.inline-link`, and only additionally calling `window.open()` when a modifier is held. Verified via a real `MouseEvent('click', ...)` dispatched directly at the `<a>` with no modifiers: `defaultPrevented` is now `true` (previously `false`).
- [x] 9.2 Fix: pressing Enter for the first time at the end of a paragraph ending in a confirmed link didn't create a new line — it triggered the "push heading down" special case instead (a blank line inserted *above*, caret jumping to the very start), because `caretOffsetInLine()` was reading a corrupted selection. Root cause: `confirmLinks()` replaces a line's plain Text child with a Text/`<a>` sequence via `child.replaceWith(...)`; when the caret's Range pointed into that exact text node (e.g. immediately after Tab-confirming a link with the caret still at the end of the line), removing that node from the DOM made the browser reset the selection to an arbitrary position (observed: the very start of the editor) — the same class of caret-loss bug already fixed once for `confirmLine`/`revertLine`, re-introduced here because `confirmLinks` didn't have the equivalent fix. Fixed by capturing the caret's line-relative offset via `caretOffsetInLine()` *before* any mutation (only when the caret was actually inside this line to begin with) and restoring it via `placeCaretAtOffset()` afterward if anything changed. Verified: confirmed a link at the very end of a paragraph via Tab, caret offset stayed at the correct end position (24, matching the full length) instead of resetting to 0; pressing Enter afterward correctly split into the original line plus a new empty paragraph below, with the caret landing in the new line — not the push-down misfire.
- [x] 9.3 Reported alongside 9.1/9.2; confirmed to be the already-documented "splitting a line resets any links inside it back to plain text" trade-off from design.md, not a new implementation defect — but real use showed the "before" half losing its link too (not just the "after" half as originally described) read as a genuine bug, not an acceptable rough edge. User decided: the "before" half should keep its link, only the "after" half should reset. Redesigned `splitLine()` to split at the DOM level instead of the flattened-string level: added `splitLineNodes(lineEl, offset)`, which walks the line's actual child nodes and returns which stay in place (kept as-is, links included) versus which move to the new line (flattened to plain text, same as any freshly created line). A text node straddling the split point is itself split in two; an atomic link is never split mid-span, since a real caret can never land inside one. Verified in the running app: (a) split after a link with trailing text — link preserved in line 1, trailing text alone in line 2; (b) split exactly at a link's end boundary (link is the last content) — link preserved, line 2 genuinely empty; (c) split before a link — link correctly resets to plain text, now entirely in line 2. Regression-checked the two pre-existing early-return special cases (heading push-down at offset 0, empty-list-item Enter-exits-list) and a plain-text-only split — all three unaffected, matching prior behavior exactly. Added two new spec scenarios ("Pressing Enter preserves a confirmed link before the split point" / "...resets a confirmed link after the split point") and updated the corresponding design.md decision and risk entries to describe the asymmetric (not symmetric) reset.
- [x] 9.4 Fix (reported as two more bugs, one root cause): pasting a URL — as opposed to typing it — into the middle or end of a line meant it never converted to a link, and pressing Enter afterward split at a completely unrelated point. Root cause, found after the user pinpointed "typing works, pasting doesn't": the browser's default paste handling for `contenteditable` doesn't insert plain text the same way typing does — it can wrap the pasted content in a `<span>` (confirmed by constructing that exact structure by hand and reproducing both symptoms). `confirmLinks()` only ever scans direct `TEXT_NODE` children and silently skips any other element, so a URL trapped inside a pasted wrapper was invisible to link detection — explaining "doesn't convert." `splitLineNodes()` then treats that same wrapper as one atomic, unsplittable unit (the same handling it gives a real link), so a caret positioned inside the *trailing* text node after the wrapper produced a split point that looked unrelated to where the user actually clicked — explaining "splits at a weird point." Rather than teaching every line-walking function to defensively handle arbitrary pasted HTML, added a `paste` handler that always intercepts the event, reads only `text/plain` from the clipboard, and inserts it via `document.execCommand('insertText', false, text)` — the same effect as typing, so paste can no longer create structure any of the line-walking functions haven't already been verified against. Verified: dispatching a synthetic `ClipboardEvent('paste', ...)` with `https://google.com` as `text/plain` now inserts a single plain text node (not a wrapped element); pasting mid-line and pressing Enter immediately after splits at the exact intended character position with the link correctly confirmed; pasting at the very end of a line and pressing Enter immediately after also correctly confirms the link and creates a new line, matching the two originally reported symptoms exactly. Regression-checked plain typing + Tab-confirm still works unaffected.
- [x] 9.5 Fix: after confirming a link, splitting the line via Enter, then Backspacing the split-off line back away, a *later* Enter split on the same (now link-containing) line landed at a completely unrelated point — not caused by typing or pasting at all, this time. Root cause: the Backspace handler's offset-0 block only ever fired for `lineEl.dataset.lineType !== 'paragraph'` — a plain paragraph at offset 0 was never handled by this feature's own code at all, at any point since headings/lists were introduced, and fell through to the browser's native `contenteditable` div-merge behavior. That native merge produces DOM structure this project's code doesn't control, and was found (via the user's exact 5-step repro: type a link-containing line, split it, Backspace-merge the split-off remainder back, then split again elsewhere) to corrupt the line's structure in a way that only surfaced on that *subsequent* split. Fixed by handling `paragraph`-type Backspace-at-offset-0 explicitly, the same way headings/lists already are: added `mergeLineIntoPrevious(lineEl, prevEl)`, which moves lineEl's actual child nodes onto the end of prevEl (not by reading/writing `.textContent`), so any link on either side survives the merge — and reused it for the existing heading-merge case too (previously flatten-based via `setLineContent`, silently dropping any link in either line on merge, a latent instance of the same class of bug that happened not to have been reported yet). Verified by replaying the user's exact 5 steps end-to-end: link stayed a real `<a>` through the Backspace-merge in step 3, and the subsequent Enter split in step 4 landed exactly at the intended character position ("012 [link] 34" / "5"), not at an unrelated one. Regression-checked: plain-paragraph-into-plain-paragraph merge, heading-into-list-item merge, heading-with-empty-spacer-above (spacer deleted, heading untouched, unaffected by this change), list-item-reverts-in-place (unaffected), and Backspace on the very first line with no preceding line (no-op) — all five matched expected behavior.
